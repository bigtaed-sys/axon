# Axon

Персональный AI-агент, у которого ядро живёт на твоей машине или сервере, а
приложения подключаются к нему и синхронизируются.

## Идея

Ядро (`core`) владеет всем: историей, памятью, инструментами, контекстом,
вызовами моделей. Клиенты — тонкие: рисуют и вводят. Из этого следует главное
свойство — сколько бы устройств ни было подключено, контекст один, кэш промпта
один, и расход токенов не умножается на число экранов.

```
        ┌──────────────── ЯДРО (демон) ───────────────────────────────┐
        │  агент-рантайм · память · инструменты · планировщик         │
        │  журнал событий (append-only, seq) · API: WS + REST         │
        └──────┬──────────────────┬───────────────────┬───────────────┘
               │                  │                   │
          десктоп            мобильное           Telegram
                              приложение         (адаптер)
```

## Три решения, на которых всё держится

**Журнал вместо синхронизации состояний.** Всё, что меняет состояние, дописывается
в append-only журнал с монотонным `seq`. Клиент помнит последний применённый seq и
при подключении просит «дай всё после N». Оффлайн, переподключение, несколько
устройств сразу — один механизм, а не три. Писатель по сути один (ядро), поэтому
CRDT здесь не нужен.

**Журнал и эфемерика разделены.** Поток токенов, фазы работы, счётчик расхода — это
сигналы: не нумеруются, не хранятся, не досылаются. Правило: если потеря не ломает
состояние — это сигнал. Иначе журнал распух бы в тысячу раз и синк на слабом канале
умер бы.

**Расход токенов виден на уровне протокола.** `Usage` отделяет `cachedInputTokens`
от обычных, вывод инструмента обрезается до `preview` со ссылкой на полный blob, у
прогона есть `budgetTokens` и `stopReason: 'budget_exhausted'`. Это не «не забудьте
оптимизировать», а форма контракта.

И это видно пользователю: в заголовке чата есть разбор «во что обходится
контекст» — сколько токенов стоит системный промпт, память, оглавление скиллов,
схемы инструментов и история, и какая часть попадёт в кэш. Обычно расход
показывают постфактум одной цифрой, с которой ничего нельзя сделать; здесь —
до отправки и по частям, каждую из которых можно уменьшить.

## Рутины

То, что агент делает сам, без человека рядом. Человек описывает задачу словами —
«каждое утро посмотри, что изменилось в папке проекта, и, если есть что сказать,
напиши сводку», — а Axon **один раз** компилирует описание в явный список шагов.
Дальше рутина исполняется детерминированно.

Компиляция, а не «запускать агента каждый раз», выигрывает по трём статьям:

- **Цена.** Рутина «каждые полчаса» — это сорок восемь прогонов в сутки. Цикл
  агента везёт с собой контекст и схемы всех инструментов; скомпилированные шаги
  не стоят почти ничего, а часто и вовсе не обращаются к модели.
- **Предсказуемость.** Фоновая задача, каждый раз заново решающая, что делать, —
  самая пугающая разновидность автоматизации. Шаги видно до включения.
- **Ошибки.** Компилятор сверяет каждый шаг с настоящими схемами инструментов:
  несуществующий инструмент, забытый обязательный аргумент или выдуманное имя
  поля всплывают при создании, а не в три часа ночи на первом прогоне.

Жёсткий конвейер при этом не умеет главного — решать по обстановке. Поэтому есть
шаг `agent`: один шаг с собственным бюджетом там, где нужно суждение, вместо
агента на каждом шагу.

Всего шагов двенадцать: вызов инструмента, вопрос модели, разбор текста на поля,
агент, ветвление, повтор по списку, переменная, уведомление, сообщение в
переписку, запись в память, пауза и досрочная остановка. Каждый прогон
записывается пошагово — видно, на чём именно рутина споткнулась.

Опасные инструменты рутина получает только поимённо: рядом нет человека, который
подтвердит действие, и подтверждать его молча нельзя.

Время следующего запуска считается наперёд и хранится в базе, а не держится
таймером: ядро на личной машине выключают и усыпляют. Проснувшись, оно видит,
что момент прошёл, и отрабатывает пропущенное.

## Плагины

Плагин — единица установки. Внутри может лежать что угодно из трёх: свои
инструменты на JS, подключения к MCP-серверам и скиллы (инструкции текстом).
Плагин без кода — законная и частая вещь: манифест из десяти строк, поднимающий
чужой MCP-сервер.

Каждый плагин работает **отдельным процессом**. Бесконечный цикл, утечка памяти
или `process.exit()` внутри плагина убивают только его: ядро видит падение,
снимает регистрацию его инструментов и продолжает работать.

Главный способ поставить что-то — **вставить конфигурацию любого MCP-сервера в
том виде, в каком она написана в его README**. Своего формата у Axon нет
намеренно: человек приходит с готовым куском JSON для Claude Desktop или VS
Code, и заставлять его переписывать это в наши поля — верный способ сделать
установку тем, чем никто не пользуется.

```json
{ "mcpServers": { "everything": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-everything"] } } }
```

Встроенный каталог — это закладки на шесть проверенных серверов, а не граница
возможного: он едет вместе с ядром, поэтому раздел не пустует без интернета.

```bash
axon plugin catalog              # что есть в каталоге
axon plugin add github           # поставить из каталога
axon plugin add-mcp конфиг.json  # свой MCP-сервер (или конфиг на stdin)
axon plugin add https://…        # поставить из репозитория
axon plugin link ./my-plugin     # подключить папку как есть (разработка)
axon plugin logs my-plugin       # что он печатает
```

Как написать свой — [packages/plugin-sdk/README.md](packages/plugin-sdk/README.md),
рабочий пример — [examples/hello-plugin](examples/hello-plugin).

### Картинки

Зрение — свойство модели, а не провайдера: у одного провайдера одновременно
бывают и обычные модели, и vision. Поэтому таблицы «этот провайдер умеет
картинки» в Axon нет — она была бы и неверной, и протухающей: модели выходят
чаще, чем обновляется ядро.

Вместо неё — **отдельная модель для распознавания**, которую выбирают в
настройках. Она описывает вложение один раз, описание остаётся в переписке
текстом, и дальше с ним работает основная модель — любая, включая текстовую.

Побочный выигрыш важнее удобства: картинка стоит токенов один раз, а не
переотправляется на каждом следующем ходу до конца разговора.

### Скиллы и бюджет токенов

Скилл — инструкция текстом, и раскрывается она в два шага. В контексте постоянно
висит только строка «есть скилл X, он про Y» — десяток токенов. Тело, которое
может быть на пять страниц, модель забирает сама инструментом `read_skill`, и
только когда оно правда понадобилось.

Разница на практике: двадцать поставленных скиллов стоят ~300 токенов в каждом
запросе вместо ~20 000. Тот же приём, что и `deferred` у инструментов, —
применённый к знаниям вместо действий. По той же причине инструменты
MCP-серверов регистрируются `deferred`: их схемы длинные, а серверов бывает
несколько.

## Установка ядра

Ядро — самостоятельная программа. Ставится на любую машину с Node 22.5+,
нативных модулей нет, компилятор не нужен.

```bash
npm install -g @axon-assistant/core
axon start                      # слушает 127.0.0.1:8787
axon start --host 0.0.0.0       # ещё и для устройств из сети
```

При первом запуске ядро печатает код для подключения первого устройства и
кладёт его в `bootstrap.code` рядом с данными — код сгорает после первого
использования. Дальше вводите его в приложении.

```bash
axon status                                     # запущено ли и где
axon secret set provider.anthropic.apiKey sk-…  # ключ провайдера
axon secret list                                # что задано (значения не показываются)
axon devices                                    # подключённые устройства
axon stop
```

Папка данных задаётся переменной `AXON_DATA_DIR`; по умолчанию — стандартная
папка приложений вашей ОС. Внутри лежит всё: база, блобы и ключ шифрования
секретов. Переносится копированием.

> Через интернет ядро стоит выставлять только за туннелем или обратным прокси
> с TLS: своего шифрования у него нет намеренно — это работа отдельного слоя.

## Десктоп

```bash
cd apps/desktop
npm run build && npx electron .
```

Приложение само поднимает ядро дочерним процессом на свободном порту и
подключается к нему как обычное устройство — по тому же протоколу, что и любой
другой клиент. Токен сохраняется в `device.json` в папке приложения.

Одна оговорка про упаковку: `better-sqlite3` — нативный модуль, и у Electron
свой ABI. Сейчас ядро запускается системным Node, под который модуль уже
собран. Для устанавливаемой сборки его нужно пересобрать под Electron
(`electron-rebuild`) — тогда внешний Node не понадобится.
